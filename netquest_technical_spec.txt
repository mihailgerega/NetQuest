# Техническое задание  
## Проект: **NetQuest — интерактивный симулятор компьютерных сетей**

**NetQuest** — это современное веб-приложение, в котором пользователь визуально строит компьютерную сеть из узлов, запускает сетевые сценарии и наблюдает, как “пакеты” проходят через DNS, ARP, TCP, TLS, NAT, firewall, proxy, load balancer, router и другие компоненты.

Проект должен выглядеть как современный интерактивный инженерный продукт: часть обучающая платформа, часть network sandbox, часть визуальный симулятор отказоустойчивых распределённых систем.

Главная цель — показать глубокое понимание:

- компьютерных сетей;
- backend-разработки на Go;
- безопасности веб-приложений;
- отказоустойчивой архитектуры;
- observability;
- real-time систем;
- проектирования сложного продукта.

---

# 1. Концепция проекта

## 1.1. Основная идея

Пользователь открывает сайт и попадает в интерактивную рабочую область, похожую на сетевую лабораторию.

Он может:

- перетаскивать на canvas сетевые устройства;
- соединять их каналами связи;
- настраивать IP-адреса, маршруты, DNS-записи, firewall-правила;
- запускать сетевые сценарии;
- отправлять виртуальные пакеты;
- видеть каждый этап прохождения пакета;
- ломать узлы и каналы;
- наблюдать failover;
- смотреть логи, трассировку, latency, packet loss;
- сохранять свои сетевые схемы;
- запускать готовые обучающие квесты.

Пример сценария:

> Пользователь создаёт клиента, DNS-сервер, firewall, load balancer и три backend-сервиса. Затем отправляет HTTPS-запрос на `api.netquest.local`. Система показывает DNS lookup, TCP handshake, TLS handshake, firewall decision, балансировку нагрузки, прохождение через NAT и ответ сервера. После этого пользователь нажимает “сломать router-1”, и трафик автоматически перестраивается через резервный маршрут.

# 4. Ключевой вау-эффект

Главная фишка проекта:

> Пользователь может построить сеть, отправить пакет и увидеть его путь в реальном времени: от DNS-запроса до TLS-handshake, firewall decision, routing lookup, NAT, load balancing и ответа сервера.

Вторая фишка:

> Пользователь может сломать узел или канал, после чего система покажет failover, перестроение маршрута и восстановление доступности.

# 6. Сетевые механики симуляции

## 6.1. ARP

Система должна уметь симулировать ARP resolution внутри одной L2-сети.

Функции:

- ARP request;
- ARP reply;
- ARP cache;
- cache expiration;
- MAC lookup;
- невозможность отправки пакета без MAC-адреса;
- отображение ARP-событий на timeline.

Пользователь должен видеть:

```text
Client-1 wants to send packet to 192.168.1.10
ARP cache miss
Broadcast ARP request: Who has 192.168.1.10?
Server-1 replies: 192.168.1.10 is at 02:42:ac:11:00:02
ARP cache updated
Packet sent
```

---

## 6.2. IP routing

Система должна поддерживать routing table lookup.

Функции:

- static routes;
- default gateway;
- longest prefix match;
- route cost;
- unreachable route;
- route recomputation после сбоя;
- TTL decrement;
- ICMP time exceeded.

Пример таблицы маршрутизации:

```text
Destination       Gateway         Interface     Cost
10.0.0.0/24       direct          eth0          0
172.16.0.0/16     10.0.0.1        eth1          10
0.0.0.0/0         10.0.0.254      eth0          100
```

---

## 6.3. ICMP

Должны поддерживаться базовые ICMP-сценарии:

- ping;
- destination unreachable;
- time exceeded;
- packet too big;
- traceroute-like flow.

UI должен показывать ping как отдельный тип сценария:

```text
Client-1 → Router-1 → Router-2 → Server-1
ICMP Echo Request
ICMP Echo Reply
RTT: 37ms
```

---

## 6.4. DNS

DNS-сервер должен поддерживать:

- A records;
- AAAA records;
- CNAME;
- MX;
- TXT;
- TTL;
- cache;
- NXDOMAIN;
- SERVFAIL;
- recursive-like simulation;
- split-horizon DNS;
- DNS propagation delay в обучающих сценариях.

Пример DNS-записи:

```json
{
  "name": "api.netquest.local",
  "type": "A",
  "value": "10.0.2.15",
  "ttl": 300
}
```

Пользователь должен видеть DNS flow:

```text
Client asks DNS: api.netquest.local
DNS cache miss
DNS Server returns A 10.0.2.15 TTL=300
Client caches result
```

---

## 6.5. TCP

Система должна симулировать:

- SYN;
- SYN-ACK;
- ACK;
- established connection;
- FIN;
- RST;
- timeout;
- retransmission;
- connection refused;
- dropped SYN;
- half-open connection.

Timeline TCP-handshake:

```text
Client → Server: SYN
Server → Client: SYN-ACK
Client → Server: ACK
TCP connection established
```

---

## 6.6. UDP

UDP должен быть представлен как connectionless flow.

Система должна показывать:

- отсутствие handshake;
- возможность потери пакета;
- отсутствие retransmission на транспортном уровне;
- использование UDP для DNS;
- использование UDP для VPN-like сценариев.

---

## 6.7. TLS

TLS-механика должна быть симулированной, не настоящей криптографической реализацией.

Должны отображаться этапы:

- ClientHello;
- ServerHello;
- certificate check;
- key exchange simulation;
- session key established;
- encrypted application data.

Ошибки TLS:

- expired certificate;
- hostname mismatch;
- untrusted CA;
- unsupported TLS version;
- handshake timeout.

Пример события:

```text
TLS certificate validation failed:
reason: hostname mismatch
expected: api.netquest.local
actual: internal.service.local
```

---

## 6.8. NAT

NAT Gateway должен поддерживать:

- source NAT;
- destination NAT;
- port mapping;
- connection tracking;
- expired NAT session;
- private-to-public mapping.

Пример NAT table:

```text
Private Address        Public Address        Protocol
10.0.1.15:49152        203.0.113.10:62001    TCP
10.0.1.16:49153        203.0.113.10:62002    TCP
```

---

## 6.9. Firewall

Firewall должен уметь принимать решение allow/deny/drop/reject.

Правило firewall:

```json
{
  "priority": 100,
  "action": "allow",
  "protocol": "tcp",
  "source": "10.0.1.0/24",
  "destination": "10.0.2.10/32",
  "port": 443
}
```

Firewall должен поддерживать:

- priority;
- allow;
- deny;
- drop;
- reject;
- source CIDR;
- destination CIDR;
- protocol;
- port;
- stateful rules;
- default policy;
- audit log decision.

UI должен объяснять решение:

```text
Packet matched rule #100:
ALLOW tcp 10.0.1.0/24 → 10.0.2.10:443
Decision: allowed
```

---

## 6.10. Load Balancer

Load Balancer должен поддерживать алгоритмы:

- round-robin;
- weighted round-robin;
- least connections;
- random;
- consistent hashing;
- latency-aware;
- health-check based routing.

Backend pool:

```json
{
  "serviceName": "api-service",
  "algorithm": "least_connections",
  "backends": [
    {
      "nodeId": "server-1",
      "weight": 1,
      "healthy": true
    },
    {
      "nodeId": "server-2",
      "weight": 2,
      "healthy": true
    }
  ]
}
```

Должно быть видно:

- какой backend выбран;
- почему он выбран;
- состояние каждого backend;
- активные соединения;
- ошибки;
- retries;
- failover.

---

## 6.11. Proxy

Proxy должен поддерживать:

- forward proxy;
- reverse proxy;
- header rewriting;
- TLS termination simulation;
- access logs;
- upstream timeout;
- retry;
- cache hit/miss.

---

## 6.12. VPN Gateway

VPN-шлюз должен показывать:

- encapsulation;
- encrypted tunnel simulation;
- tunnel status;
- keepalive;
- reconnect;
- route through tunnel;
- split tunnel;
- full tunnel.

---

## 6.13. Packet loss, latency, jitter

Каждый канал должен влиять на прохождение пакета.

Симулятор должен учитывать:

- latency;
- jitter;
- packet loss;
- bandwidth;
- queueing delay;
- overloaded node;
- timeout.

Пример:

```text
Packet entered link router-1 → router-2
Base latency: 20ms
Jitter: +4ms
Packet loss: 2%
Result: packet delivered in 24ms
```

---

## 6.14. Failover

Failover — один из центральных сценариев проекта.

Система должна поддерживать:

- ручное отключение узла;
- ручное отключение канала;
- автоматическое обнаружение сбоя;
- health checks;
- route recomputation;
- load balancer backend removal;
- retry на другой backend;
- degraded mode;
- восстановление после сбоя.

Пример:

```text
Router-1 status changed: healthy → down
Health check failed
Route via Router-1 removed
Alternative route found via Router-2
Traffic restored
Downtime: 430ms
```

# 7. Режимы работы приложения

## 7.1. Sandbox Mode

Свободный режим.

Пользователь сам строит сеть, настраивает узлы, запускает симуляции.

Функции:

- создать схему;
- добавить узлы;
- соединить узлы;
- настроить параметры;
- отправить пакет;
- сломать узел;
- сохранить схему;
- экспортировать JSON;
- импортировать JSON.

---

## 7.2. Quest Mode

Обучающие сценарии.

Примеры квестов:

1. **“Почему не работает сайт?”**  
   Нужно найти проблему в DNS.

2. **“Firewall блокирует трафик”**  
   Нужно исправить правило.

3. **“Backend недоступен после падения router-1”**  
   Нужно настроить резервный маршрут.

4. **“TLS certificate mismatch”**  
   Нужно исправить hostname сертификата.

5. **“Load balancer отправляет трафик на мёртвый backend”**  
   Нужно включить health checks.

6. **“NAT не выпускает клиента в интернет”**  
   Нужно настроить source NAT.

7. **“Packet loop”**  
   Нужно найти ошибку маршрутизации.

Каждый квест должен иметь:

- описание проблемы;
- стартовую схему;
- цель;
- ограничения;
- систему проверки;
- подсказки;
- финальный отчёт.

---

## 7.3. Demo Mode

Публичный режим без авторизации.

Пользователь может открыть готовые демо-сценарии:

- DNS resolution;
- TCP handshake;
- TLS handshake;
- firewall allow/deny;
- NAT;
- load balancing;
- failover;
- traceroute;
- packet loss.

Ограничения demo mode:

- нельзя сохранять приватные проекты;
- ограниченное число запусков в минуту;
- ограниченный размер топологии;
- нельзя импортировать произвольные большие JSON-файлы.

---

## 7.4. Battle Mode / Challenge Mode

Дополнительный режим для вау-эффекта.

Пользователю даётся сломанная сеть, и он должен восстановить связность.

Пример:

> Сделай так, чтобы Client-1 смог получить HTTPS-ответ от api.netquest.local, при этом firewall должен разрешать только порт 443, а backend-2 должен оставаться недоступным напрямую.

Система оценивает:

- корректность;
- безопасность;
- минимальность изменений;
- время решения;
- количество попыток.

# 12. Simulation Engine

## 12.1. Основная идея движка

Simulation Engine не должен отправлять реальные сетевые пакеты. Это безопасный виртуальный движок, который моделирует сетевые события.

Симуляция должна быть:

- deterministic при одинаковом seed;
- ограниченной по ресурсам;
- пошаговой;
- воспроизводимой;
- сериализуемой;
- безопасной;
- изолированной от хоста.

---

## 12.2. Event-driven модель

Внутри симулятора всё должно быть событием.

Пример событий:

```go
type EventType string

const (
    EventPacketCreated      EventType = "packet.created"
    EventPacketForwarded    EventType = "packet.forwarded"
    EventPacketDropped      EventType = "packet.dropped"
    EventDNSQuery           EventType = "dns.query"
    EventDNSResponse        EventType = "dns.response"
    EventARPRequest         EventType = "arp.request"
    EventARPReply           EventType = "arp.reply"
    EventTCPHandshakeStart  EventType = "tcp.handshake.start"
    EventTCPHandshakeDone   EventType = "tcp.handshake.done"
    EventTLSHandshakeStart  EventType = "tls.handshake.start"
    EventTLSHandshakeDone   EventType = "tls.handshake.done"
    EventFirewallDecision   EventType = "firewall.decision"
    EventRouteSelected      EventType = "route.selected"
    EventLBBackendSelected  EventType = "lb.backend.selected"
    EventNodeFailed         EventType = "node.failed"
    EventFailoverTriggered  EventType = "failover.triggered"
)
```

Каждое событие должно содержать:

```go
type SimulationEvent struct {
    ID            string                 `json:"id"`
    SimulationID  string                 `json:"simulationId"`
    Type          EventType              `json:"type"`
    TimestampMs   int64                  `json:"timestampMs"`
    SourceNodeID  string                 `json:"sourceNodeId,omitempty"`
    TargetNodeID  string                 `json:"targetNodeId,omitempty"`
    PacketID      string                 `json:"packetId,omitempty"`
    Severity      string                 `json:"severity"`
    Message       string                 `json:"message"`
    Details       map[string]any         `json:"details"`
}
```

---

## 12.3. Packet model

```go
type Packet struct {
    ID              string
    Protocol        Protocol
    SourceNodeID    string
    Destination     Destination
    SourceIP        string
    DestinationIP   string
    SourcePort      int
    DestinationPort int
    TTL             int
    SizeBytes       int
    State           PacketState
    Path            []Hop
    Metadata        map[string]any
}
```

## 12.4. Simulation run

Пользователь запускает сценарий:

```json
{
  "type": "https_request",
  "sourceNodeId": "client-1",
  "target": "https://api.netquest.local/users",
  "method": "GET"
}
```

Движок должен:

1. Проверить схему.
2. Найти client node.
3. Выполнить DNS resolution.
4. Выполнить ARP при необходимости.
5. Построить route.
6. Пройти firewall.
7. Выполнить TCP handshake.
8. Выполнить TLS handshake.
9. Передать application request.
10. Пройти load balancer.
11. Получить ответ от backend.
12. Вернуть response path.
13. Сгенерировать timeline событий.

---

Должны быть режимы:

- run all;
- step next;
- pause;
- resume;
- reset;
- replay;
- speed control.

Это важно для образовательного эффекта.

# 14. Безопасность

Безопасность должна быть встроена в архитектуру, а не добавлена потом.

## 14.1. Главный принцип безопасности

NetQuest — это **симулятор**, а не инструмент для реального сканирования сетей.

Запрещено:

- выполнять реальные DNS-запросы от имени пользователя без строгих ограничений;
- сканировать IP-адреса;
- подключаться к произвольным хостам;
- отправлять реальные пакеты;
- выполнять пользовательский код на сервере;
- использовать пользовательские URL для серверных запросов без защиты.

Все сетевые действия должны быть виртуальными.

# 15. Отказоустойчивость

## 15.1. Основные требования

Система должна быть спроектирована так, чтобы отказ одного компонента не ломал всё приложение.

Требования:

- stateless API;
- горизонтальное масштабирование;
- Redis для cache/rate limit;
- PostgreSQL как источник истины;
- NATS для асинхронных событий;
- graceful shutdown;
- health checks;
- readiness/liveness probes;
- retry with backoff;
- circuit breakers;
- idempotency keys;
- transactional outbox для важных событий;
- автоматическое восстановление WebSocket-сессии на frontend.

---

## 15.2. Stateless API

API-сервисы не должны хранить пользовательское состояние в памяти.

Состояние хранится:

- PostgreSQL — проекты, пользователи, схемы;
- Redis — cache, rate limit, temporary simulation state;
- NATS — event streaming;
- object storage — экспортированные файлы, если понадобится.

---

## 15.3. Graceful shutdown

При остановке backend должен:

1. Перестать принимать новые запросы.
2. Завершить текущие HTTP-запросы.
3. Закрыть WebSocket-сессии корректным сообщением.
4. Дождаться завершения активных simulation jobs или сохранить их состояние.
5. Закрыть соединения с БД, Redis, NATS.
6. Завершиться без потери данных.

---

## 15.4. Health checks

Endpoint:

```text
GET /health/live
GET /health/ready
GET /health/deep
```

`/health/live`:

- процесс жив.

`/health/ready`:

- доступна БД;
- доступен Redis;
- доступен NATS;
- миграции актуальны.

`/health/deep`:

- проверка записи/чтения в Redis;
- ping PostgreSQL;
- publish/consume test event в NATS.

---

## 15.5. Circuit breaker

Использовать для:

- Redis;
- NATS;
- external OAuth providers;
- background workers.

Если Redis недоступен:

- API продолжает работать в degraded mode;
- rate limit переключается на локальный in-memory лимит;
- cache отключается;
- пользователь получает предупреждение только при необходимости.

Если NATS недоступен:

- симуляции можно запускать синхронно в ограниченном режиме;
- events сохраняются в outbox;
- после восстановления NATS события публикуются.

---

## 15.6. Idempotency

Для операций создания:

```text
POST /projects
POST /simulations
POST /topologies/import
```

Поддержать `Idempotency-Key`.

Это защитит от дублирования при retry.

---

## 15.7. WebSocket reconnect

Frontend должен:

- автоматически переподключаться;
- показывать статус соединения;
- не терять состояние canvas;
- после reconnect запрашивать последние события;
- продолжать replay симуляции.

---
